## Lessons Learned

- **When troubleshooting a data-delivery pipeline with multiple layers (GPS hardware →
  fused provider → app, or any similar producer→intermediary→consumer chain), inspect
  the delivery chain directly (e.g. `dumpsys location`, a message-queue's consumer lag,
  a proxy's access log) as the FIRST diagnostic step, not the third.** Retrying the same
  approach with different parameters (bigger jump, more points, more time) only tells
  you "still broken," not "broken *here*" — go straight for the tool that shows you
  which layer is actually failing.
- **A plan's own pre-written fallback should be trusted on the first confirmed failure
  of the primary approach, not re-litigated after multiple retries.** If you wrote the
  fallback into the plan because you already judged the primary approach genuinely
  risky, don't spend extra unplanned effort re-proving that risk was real before using
  the fallback you already designed for exactly this situation.
- **A "do the same process on a different project" request is not a rerun — the new
  project's own architecture determines what "the same process" actually requires.**
  Lumine's realistic data came from a file upload; PawsAndPace's came from GPS activity
  — recognizing that difference up front (via the second, mechanics-specific research
  pass) is what made the GPS-fidelity question worth asking at all, rather than
  assuming the previous project's seeding approach would transfer directly.
