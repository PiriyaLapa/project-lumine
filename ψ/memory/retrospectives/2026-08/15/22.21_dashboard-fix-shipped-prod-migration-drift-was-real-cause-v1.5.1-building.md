Caught it by noticing the output didn't match `alembic current`'s reported state, not because I anticipated the gotcha — this could easily have gone differently with a less attentive read of a large SQL dump.

## Lessons Learned

- When diagnosing any production bug, check the production database's actual live migration/schema state directly (e.g., `alembic current` against the real `DATABASE_URL`) *before* building or trusting any root-cause theory — dev/prod schema drift can itself be the entire bug, and no amount of local-environment or git-history evidence substitutes for that one live check.
- Alembic's `--sql` (offline) mode ignores the database's actually-tracked current revision unless you pass an explicit `current:head` range — an unscoped `alembic upgrade head --sql` will regenerate the full migration chain from `base`, which can look alarmingly like "this will recreate everything" when dry-running against a real target. Always scope the range explicitly when previewing a production migration.
- When `adb`/TCP connections succeed but no application data comes back, suspect the reverse-tunnel/relay layer specifically, not raw network reachability — test both the tunneled path and a direct-IP path before concluding the network itself is unreachable.
- For any non-trivial adb UI automation, pull `uiautomator dump` for exact element bounds before the first tap, not after coordinate-guessing has already failed once or twice.
