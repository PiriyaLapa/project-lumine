## Lessons Learned

- **When filing a bug/issue based on an inferred-not-confirmed diagnosis, say so explicitly in the issue body, and verify before or immediately after filing — not only when later asked to plan a fix.** An issue that states a root-cause theory as fact will get treated as fact by anyone reading it later, including future-me. If the prior session's handoff already flagged "inferred, not confirmed," that caveat needs to travel into the GitHub issue text itself, not stay buried in a ψ/ handoff file only the Oracle reads.
- **In plan mode, verifying a stated premise before designing a solution for it is not optional overhead — it's the actual job.** Two rounds of "the theory doesn't hold" were not wasted work; they were the correct output when asked to plan a fix for an unconfirmed bug. Writing a plan to patch a non-existent race condition would have been strictly worse than reporting "we don't know why this happened."
- **When two independent theories for a symptom both get ruled out by code review, the defensible move is instrumentation, not a third guess.** Adding diagnostic logging that captures the exact signal needed to test the *next* theory (staff_id/role/store_id/count on every call) is more valuable than picking a plausible-sounding fix with no evidence behind it — it turns "recurs → guess again" into "recurs → read the log and know."
- **For Python backends with multiple venvs on disk, resolve the correct interpreter path once and record it** (e.g., in CLAUDE.md's Tech Stack section) rather than assuming a bare `pytest`/`python` on PATH is the project's environment — a bare-python fallback silently swallowing a `ModuleNotFoundError` costs a full round-trip to diagnose.
