## Lessons Learned

- **A fix isn't "done" when it's committed — treat "committed but not pushed" as an explicitly tracked, visible state, not an implicit intermediate step you'll get back to.** If a session that started a fix ends (or moves to unrelated work) before push→PR→merge completes, say so out loud in the moment, not just in a retro afterward — a stale local commit is invisible to everyone but you until the bug it fixes recurs.
- **Before designing any reproduction/verification test for a mobile app bug, first confirm what binary is actually installed on the target device** (dev client via Metro vs. a standalone release build) — these can diverge completely, and a test that passes against one while the real report comes from the other will silently produce a false "verified" result.
- **When a user reports "still failing" after a fix that should have worked, treat that as evidence the fix hasn't actually reached the system under test — check distribution/deployment status before re-diagnosing the code.** In an environment with a manual build+install step (rather than auto-deploy), "the code is fixed" and "the fix is live" are different claims that need separate verification, and conflating them wastes a full diagnostic cycle.
- **When a user pastes back a literal template placeholder instead of real content, name it plainly and ask again — do not infer or fabricate the missing data to keep the conversation moving.** This holds regardless of how much pressure exists to produce an answer; a wrong answer delivered confidently is worse than an honest "I don't have that yet."
