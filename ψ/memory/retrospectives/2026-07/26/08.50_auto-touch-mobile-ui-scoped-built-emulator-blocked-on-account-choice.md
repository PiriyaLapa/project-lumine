## Honest Feedback

**Friction 1 — WSL2 + Windows-hosted-emulator networking has no error signal for the actual failure mode.** `adb reverse tcp:8081 tcp:8081` printed success and showed up cleanly in `adb reverse --list`, giving zero indication that it wasn't actually forwarding traffic. I only found the real problem by manually testing connectivity at three different layers (Windows PowerShell, device-side `nc`, device-side Chrome) — a "did adb reverse silently no-op" check should have been step one, not step four.

**Friction 2 — Expo Go's crash rate this session (7/7 failures before success, including immediately after a genuine cold boot) is worse than the "roughly 1-in-8 to 1-in-10" rate implied by prior sessions' notes.** This is now documented across three separate sessions as a standing, unresolved cost on every single emulator verification pass in this project — it is not an occasional fluke, it's closer to a tax that should be budgeted for explicitly rather than re-discovered each time.

**Friction 3 — the shared dev/production TiDB database has no obvious "safe to mutate" account without asking.** Every account with real due Auto-Touch data either belongs to Benz's own dogfood identity or is an old throwaway from a prior session's QA pass with no documented password. There's no lightweight, self-service way to get a fresh disposable account with real due tasks short of importing SAP data through the proper pipeline — which is correct per Rule 7, but means "verify live" and "don't touch real data" are in real tension for this specific feature every time.

## Lessons Learned

1. When a Windows-hosted Android emulator is paired with a WSL2-wrapped `adb.exe`, `adb reverse` can register successfully (appears in `adb reverse --list`, prints the port, no error) while forwarding no actual traffic. Treat "the command didn't error" as zero evidence of connectivity in any host/guest network split with a loopback alias (`10.0.2.2`, `adb reverse`, Docker's `host.docker.internal`, etc.) — get one real round-trip confirmation (a device-side request that returns actual content) before building anything on top of the assumed tunnel. In this specific WSL2 + Windows-emulator combination, pointing the guest device at the WSL2 interface's own IP (`hostname -I`) directly, bypassing the loopback alias entirely, was the fix that actually worked.

2. A lesson already sitting in memory from a prior session is not "recalled" just because it was read — under the pressure of a live, recurring failure, there's a real pull toward retrying obvious variations of the already-failed approach before reaching for the specific documented fix. When a failure signature matches something already named in memory (error text, stack trace shape, symptom description), do a deliberate check — "have I already written down what fixes exactly this?" — *before* the first retry, not after several.
