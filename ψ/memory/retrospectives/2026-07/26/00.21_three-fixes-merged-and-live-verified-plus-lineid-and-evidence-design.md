## Honest Feedback

**Friction 1 — repeated screenshot-coordinate scaling errors during ADB-driven emulator testing.**
Displayed image coordinates (900×2000) needed a consistent ×1.2 conversion to real device pixels
(1080×2400), and I applied it inconsistently across many taps, causing wrong buttons to be hit
(Logout vs. Upload SAP, a Dismiss button missed twice, task-card navigation failing three times in
a row before I switched to `uiautomator dump` bounds). This alone accounted for a large fraction of
the tool calls in the emulator-verification portion of the session.

**Friction 2 — the Expo Go `UIManager` crash is real but not fully solved.** The dependency
alignment fix clearly reduced its frequency (confirmed via clean bundler logs with no more
version-mismatch warnings), but it recurred a second time later in the same session on a
freshly-cold-booted emulator, requiring a second full cold boot to get a clean run for the merge
verification. The honest state is "significantly better, not eliminated" — worth not overclaiming
this as permanently fixed in future sessions.

**Friction 3 — no fast way to know which store/staff a given piece of local seed data belongs to.**
Registering a throwaway `store_manager` account for store 8901 produced zero tasks; had to query
the local MySQL container directly (`follow_up_tasks` → `transactions` → `staff.store_id`) to
discover the real seed data lived under store 8902. This is a one-time cost for this local DB's
current state, but it's exactly the kind of thing that would be worth a documented "which
store/staff has real test data" note if local emulator testing becomes routine.

## Lessons Learned

- **When driving an Android emulator via `adb shell input tap` against a scaled-down screenshot,
  skip screenshot-coordinate math entirely and use `uiautomator dump` to get exact on-device
  element bounds instead.** Screenshot coordinates require a conversion factor that's easy to
  compute once and easy to silently drop on later taps under time pressure — `uiautomator dump`
  bounds are already in real device pixels and remove the whole error class.
- **A single successful run after an intermittent/non-deterministic bug fix is evidence, not
  proof — verify it survives at least a second cold start in the same session before describing it
  as resolved,** especially for native-bridge race conditions where "fixed" and "less frequent" can
  look identical after just one clean pass.
- **Before registering test accounts or seeding data to reach a specific existing dataset, query
  the database directly to confirm which entity (store, staff, customer) the real data actually
  belongs to — don't guess-and-check through the UI.** A single read-only query settles it faster
  than several rounds of register → log in → observe empty state.
- **When a user's framing implies "build X" (e.g. "build a new table"), check whether X already
  exists before designing it from scratch** — the existing `import-crm` endpoint would have been
  invisible if the request had been taken at face value instead of explored first.
