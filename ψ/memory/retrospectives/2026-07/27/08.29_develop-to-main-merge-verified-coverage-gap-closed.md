Three friction points, specific to this session:

I picked `.venv` somewhat arbitrarily after checking both worked — harmless here, but it's the kind of ambiguity that could silently diverge (different installed versions) if nobody ever reconciles it.

2. **Plan-mode's read-only restriction created a real blind spot in research, not just a formality.** The test-coverage research subagent correctly refused to run `pytest` under the plan-mode restriction and fell back to static analysis (grepping `def test_` counts). That's the right call under the rule, but it meant the *coverage percentage* — the actual finding that mattered — wasn't available until the execution phase, one full round-trip later. The 295-count was accurate; the coverage number the count implied ("must be fine, right?") was not.

3. **GitHub branch protection check cost a round trip for an expected answer.** `gh api .../branches/main/protection` returning 403 (private repo, free plan) was predictable given the repo's visibility, but I hadn't confirmed visibility first — checked protection, got the 403, then had to separately confirm `visibility: PRIVATE` to explain it. Cheap, but avoidable with a different check order.

## Lessons Learned

- **A count is not a verification.** When a plan step's justification says "tests pass," that claim needs an actual run this session, not a grep for `def test_` or a citation of a prior session's number — especially when the plan gates a production-adjacent action. Test-function count and coverage percentage are independent signals; one passing does not imply the other is met.
- **Read-only research phases (plan mode, research subagents) can produce confident-sounding static findings that hide the one number that actually matters** (here: coverage %, not test count). When a restriction blocks getting the real signal, say so explicitly in the findings rather than letting a plausible proxy metric stand in for it — and revisit for real once execution is unblocked.
- **Credential handling has two distinct cases, not one.** Self-generating a throwaway credential (registering a test account, minting a scoped token) applies when the agent itself has the authority to create it. For externally-issued secrets the agent cannot mint (a third-party API key tied to the user's own account/billing), the safest pattern is different: have the user edit the secret file directly, outside the chat pipeline entirely — not "relay it" and not "run a `!` command that echoes it into history" either, since both still put the raw value through the session's visible transcript.
